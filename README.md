# Local Gear Advisor

Repository: https://github.com/Madchristian/local-gear-advisor

*[Deutsch](README.de.md)*

Local SimulationCraft-powered gear comparison for WoW Retail. The MVP reads a complete
`/simc` export including bag items, generates direct `profileset` variants, runs `simc.exe`,
validates the JSON2 report, and merges the results of every analyzed character/spec profile
into a shared `Results.lua`.

Results reach the game either via a one-time reviewed addon installation, or -- for every
analysis after that -- by pasting a small integrity-checked transport blob into the addon's own Import
tab while WoW keeps running. See [In-game workflow](#in-game-workflow) below.

## Current MVP

- all 40 class/spec combinations contained in the pinned SimulationCraft revision `5a982a3`, via a deterministically generated registry; including Guardian Druid (`104`) and Vengeance Demon Hunter (`1480`)
- tooltip addon targeted specifically at WoW Retail 12.0.7 and the official SimulationCraft addon 12.1.0-01
- rings and trinkets are tested against both slots
- configurable minimum item level filter (GUI/CLI default 282); equipped baseline gear is never filtered
- other candidates against their own slot; weapon candidates are transparently excluded and never simulated or published
- real SimC DPS comparisons including procs, special effects, talents, and set bonuses as modeled by SimC
- exact candidate identity via the item options generated by the official SimulationCraft addon
- in-game validity check against character, realm, region, level, race, spec, talent string, Omnium talents, and every relevant gear slot
- results show scenario, SimC version, and age; treated as stale after seven days
- fails closed on secret values, unreadable state, or a changed baseline profile
- `Results.lua` is only published atomically after a complete, validated JSON2 report
- schema 2 holds multiple characters and multiple specs per character; one analysis only ever replaces the exact matching identity of region, realm, character name, and numeric spec ID
- the addon selects only the exactly logged-in character and active spec; a missing, duplicate, or malformed profile never shows another character's result
- the legacy Results-only file publisher checks WoW immediately before every mutation and refuses `running` or `unknown`; because a process check cannot prevent a user from starting WoW in the following instruction window, WoW must remain closed for the entire operation
- **new:** an in-game Import tab lets you paste an integrity-checked transport blob and activate it immediately, with no reload and no file write to the live WoW tree at all -- see [In-game workflow](#in-game-workflow)
- no cloud, no telemetry, no Raidbots upload

## In-game workflow

Once the addon's code has been installed the one reviewed time (see
[Installation as a Python package](#installation-as-a-python-package)), every later analysis
can be run **without ever closing WoW again**. Nothing here writes to the live WoW tree; the
addon only ever changes its own SavedVariables, in memory, in the running session.

1. **Export, in WoW.** Open Local Gear Advisor (`/lga`, the minimap button, or the Blizzard
   Addon Compartment icon), go to the **Analyse** tab, and click "Generate export". This calls
   the official SimulationCraft addon's own documented method,
   `SimulationcraftAPI:GetSimcProfile(false, false, false, nil)`, and shows the resulting text
   already selected and focused. WoW addons cannot write to the OS clipboard, so copy it
   yourself with **Ctrl+C** -- there is no "copied" claim you have to trust.
2. **Analyze, on the desktop.** Paste (Ctrl+V) that export into the desktop companion's
   `/simc` export box and click "Analyze locally". This runs the exact same local SimC pipeline
   as before (see [CLI](#cli)/[GUI](#gui)) and, on success, fills a second read-only box,
   "Import text for /lga in-game", with a small integrity-checked transport blob. Click "Copy import text"
   to put it on the OS clipboard (the desktop app *can* touch the real clipboard).
3. **Check, in WoW.** Switch back to WoW (still running), open the **Import** tab, paste
   (Ctrl+V) the transport text, and click "Check". This only decodes and validates the blob
   against the exact same semantic schema `Results.lua` entries already have to satisfy --
   it never mutates SavedVariables.
4. **Import.** Click "Import". This is the only point anything is written: the checked
   profile activates immediately (no `/reload`, no logout). Import is only enabled for the
   *exact* text that was just Checked -- any edit to the box invalidates it and requires a
   fresh Check.
5. **Profiles.** The **Profiles** tab lists every locally known character/spec, both imported
   and from the staged results file, with its scenario, item count, age, and source. Imported
   profiles can be deleted (a second confirming click); the last apply or delete can be undone
   with one click, as long as nothing else has touched that identity's entry since.

Imported profiles and the one-step undo snapshot are account-wide SavedVariables. Apply is
immediate in memory. WoW normally flushes them to disk on logout or `/reload`; a client or OS
crash before that flush can lose the latest import. A reload is therefore optional for immediate
use, but recommended once after an important import when durable disk persistence matters.
Deleting an imported override can reveal the older embedded `Results.lua` fallback again; the UI
reports that transition explicitly.

This closes the loop the original MVP left open: previously, getting a new result in front of
the tooltip required closing WoW, letting the desktop app write `Results.lua` into the live
`AddOns` folder, and reopening WoW. Now that file write only ever happens for the one-time
addon *code* install; every routine re-analysis after that stays entirely in-session.

## Deliberately not yet included

- full top-gear combinatorics across several simultaneous upgrades
- robust defensive tank metrics; the MVP evaluates DPS
- robust healer metrics; for healers too, the result is strictly an offensive DPS comparison
- live data exchange while WoW is running for anything other than the integrity-checked in-game import transport described above; file-based exchange refuses a `running` or unknown preflight, but cannot atomically prevent WoW from being launched immediately after a successful process check
- evaluation of items that were not present in the imported bag scope
- reliable detection of every silently missing SimC effect model: explicit SimC warnings are blocked, but a special effect SimC ignores without a warning is not yet automatically provable in the MVP

## Requirements

1. Official SimulationCraft WoW addon `12.1.0-01` for the `/simc` export. Other serializer versions are not claimed to be compatible.
2. Windows build of SimulationCraft for WoW `12.0.7.68887` with `simc.exe`; other DBC/build combinations are rejected fail-closed.
3. Python 3.11+; `uv` is used for development.

### Updating the specialization registry

The runtime uses no AI and never guesses spec IDs. The checked-in
`src/local_gear_advisor/data/spec_registry.json` is generated from the public SimulationCraft
file `sc_specialization_data.inc`, pinned to one concrete git revision. For the revision
currently in use it can be reproduced and checked without network access:

```text
.venv\Scripts\python.exe tools\generate_spec_registry.py \
  --revision 5a982a3 \
  --source tests\fixtures\sc_specialization_data.inc \
  --check
```

When moving to a new SimC revision, the same command without `--source` generates the
registry directly from the HTTPS source pinned to that revision. Redirects, oversized or
incomplete sources, unknown class prefixes, duplicate IDs, and missing classes are all
rejected fail-closed. Only after review and a full test pass is the generated registry
checked in. The JSON2 report must then report that exact same SimC git revision.

## Installation as a Python package

The checked-in addon source lives at `addon/LocalGearAdvisor`; it is never runtime staging.
Whether running from the repository or an installed wheel, successful results and reviewed addon
staging files are generated outside the source checkout under this user path:

```text
%LOCALAPPDATA%\LocalGearAdvisor\addon\LocalGearAdvisor
```

Staging remains the source of truth there too. The explicitly enabled GUI/CLI live option only
publishes `Results.lua` and requires the installed code files to be byte-exact for this version;
it deliberately is **not** a code updater.

Create a complete, byte-read-back manual installation source from either the repository
environment or an installed wheel:

```text
local-gear-advisor stage-addon --output C:\Temp\LocalGearAdvisor-Staging
```

The output path must not already exist. The command writes only to that staging path, includes
all seven code files plus the empty schema-2 `Results.lua`, and never writes into WoW.
If staging fails, its randomly named hidden sibling directory is intentionally retained for
inspection instead of being deleted by pathname; this avoids deleting a concurrently replaced
directory generation. If post-publish readback fails, the target is likewise retained as
quarantine and the command reports failure. A successful publish leaves no private staging.

For the one-time program update, WoW must first be confirmed closed. Then copy
`LocalGearAdvisor.toc`, `Localization.lua`, `Sha256.lua`, `Core.lua`, `Import.lua`,
`Minimap.lua`, and `UI.lua` from reviewed staging into the addon directory. On an update, keep
the existing `Results.lua`, and back up the complete addon directory outside the live tree
before replacing code. On a first install with no existing addon, copy the complete staging
directory including its empty schema-2 `Results.lua`. Files below `WTF` are never changed. Once
this one-time code install has happened, every later analysis can use the in-game
[Import workflow](#in-game-workflow) instead -- WoW no longer needs to be closed for it.
Keep WoW closed until the complete copy and hash readback have finished: no userspace process
query can atomically lock out a later manual launch of `Wow.exe`.

## GUI

Once set up, the interface can be started directly by double-clicking:

```text
Start-LocalGearAdvisor.cmd
```

Alternatively:

```text
.venv\Scripts\local-gear-advisor.exe gui
```

Under Git Bash:

```text
.venv/Scripts/local-gear-advisor.exe gui
```

In the GUI:

1. Select the `simc.exe` executable; `SimulationCraft.exe` is rejected. If SimulationCraft is not
   installed yet, "Download SimulationCraft…" opens the fixed official HTTPS download page
   `https://www.simulationcraft.org/download.html` in the default browser. The helper never downloads
   or runs an installer itself.
2. Select the installed `Interface/AddOns/LocalGearAdvisor` folder. With exactly one unambiguous default location found, it is only ever pre-selected read-only.
3. In WoW, run `/simc` (or use the addon's own Analyse tab, see [In-game workflow](#in-game-workflow)); do not use `nobags`.
4. Paste the full export, or load it from a UTF-8 file.
5. Choose `Patchwerk` for single target, or `DungeonSlice` as the experimental M+ scenario.
6. Set the minimum item level (`282` is the default; `0` disables the filter).
7. Click "Analyze locally".

The shared result and its canonical JSON state are always generated outside the source checkout:

```text
%LOCALAPPDATA%\LocalGearAdvisor\addon\LocalGearAdvisor\Results.lua
%LOCALAPPDATA%\LocalGearAdvisor\state\profiles.json
```

An empty, whitespace-only, or relative `LOCALAPPDATA` value falls back to the absolute
`%USERPROFILE%\AppData\Local` path. The source addon's `Results.lua` is rejected as an analysis
target even when supplied explicitly.

Once analysis finishes, a read-only "Import text for /lga in-game" box fills with an integrity-checked
transport blob; "Copy import text" puts it on the OS clipboard so you can switch to WoW and
paste it into the addon's Import tab (see [In-game workflow](#in-game-workflow)) -- this needs
no file installation and works with WoW still running.

If auto-install is enabled, only `Results.lua` is ever taken over afterward. If WoW is
running, or its state is unknown, staging is left untouched. After closing WoW, "Install now"
can take over that same validated SHA-256 file without rerunning SimC. `Core.lua`, the TOC,
and SavedVariables are never overwritten by this; they are only ever checked for compatibility
or for being unchanged.

## In-game addon

- **Slash command:** `/lga` toggles the window.
- **Minimap button:** draggable around the ring; can be shown/hidden from Settings, and both
  its angle and visibility persist in `LocalGearAdvisorSettings` across sessions. The Blizzard
  Addon Compartment icon also toggles the window, defensively guarded so a future API change
  there can never surface as an unhandled Lua error.
- **Analyse tab:** generates the `/simc` export in place via the official SimulationCraft
  addon and shows it selected for a manual Ctrl+C copy (see step 1 of
  [In-game workflow](#in-game-workflow)).
- **Import tab:** paste the desktop companion's transport text, Check it (validate only, no
  mutation), then Import it (the only place SavedVariables are ever written). Editing the text
  after a Check immediately disables Import again until it is Checked again.
- **Profiles tab:** lists every locally known character/spec profile, both imported and from
  the staged results file, with scenario, item count, age, and source; imported profiles can
  be deleted (second click confirms) and the last apply/delete can be undone.
- **Settings tab:** window scale presets, window position reset, and minimap button
  visibility -- all persisted.
- **Localization:** all user-facing strings live in one file (`Localization.lua`); `deDE` is
  fully translated, every other locale falls back to `enUS`, and there is no partial/mixed
  locale table.
- **Tooltip:** an item's comparison is only ever shown for an *exact* variant match -- same
  item options (enchant/gems/bonus IDs/crafted stats), same character/spec/level/race, same
  talent and Omnium-talent string, same equipped baseline gear, same WoW/SimC build, and not
  older than seven days. Anything else fails closed silently or shows an explicit stale/unknown
  reason; an item is never scored as a zero DPS change just because SimC did not model it.

## CLI

```text
.venv/Scripts/local-gear-advisor.exe analyze \
  --input character.simc \
  --simc "C:/SimulationCraft/simc.exe" \
  --iterations 1000 \
  --min-item-level 282 \
  --fight-style Patchwerk
```

The CLI stays staging-only by default. A live installation must be explicitly enabled and
scoped to the addon folder:

```text
.venv/Scripts/local-gear-advisor.exe analyze \
  --input character.simc \
  --simc "C:/SimulationCraft/simc.exe" \
  --install-live \
  --addon-dir "C:/Games/World of Warcraft/_retail_/Interface/AddOns/LocalGearAdvisor"
```

Existing schema-1 archives produced by the project's own generator can be migrated tightly and
explicitly into the shared schema-2 state without executing any Lua:

```text
.venv/Scripts/python.exe tools/import_v1_results.py archive-a/Results.lua archive-b/Results.lua
```

The migration parser only accepts a single literal `LocalGearAdvisorResults` assignment with
the exact legacy field schema; Lua calls, extra fields, duplicate keys, and other structures
are rejected.

## Data sources and Armory limits

Battle.net Armory could in the future optionally supply a character list, public profile data,
and equipped gear. However, it does not reliably include bags, character bank, reagent bank,
warband bank, or every local item variant. It is therefore not a substitute for a complete
local `/simc` export. A later Armory integration remains opt-in and needs a defined OAuth,
privacy, region/realm, rate-limit, cache, and fail-closed contract before implementation. For
complete candidate data, `/simc` remains the default; in the long run, an account-wide local
addon collector could capture already-loaded gear, bags, and bank areas in SavedVariables.

## Security model

- The ingested SimC baseline is reconstructed from a narrow allowlist. Duplicate directives, invalid bound metadata, and output/file/include/import/network directives are all rejected.
- Unreadable bag lines, incomplete baseline gear, and the titan-disc belts that can only be fully serialized via tooltip parsing block the entire run; old `Results.lua` data stays unchanged.
- With the filter enabled, candidates below the chosen minimum item level or with an unknown item level are first deduplicated by fingerprint and excluded. Remaining weapon slots are then reported as unsupported. None of these categories are ever simulated or published to `Results.lua`.
- Subprocesses use an argument list with `shell=False`.
- A SimC error, timeout, warning/error log, missing provenance, mismatched scenario, wrong DBC/WoW version, mismatched iteration count, missing JSON2 report, or incomplete profileset result all block publication.
- A missing, structurally invalid, or revision-mismatched specialization registry blocks publication. The build/CI check additionally ensures the checked-in registry is byte-reproducible from the pinned source snapshot. Unknown class/spec pairs stay fail-closed.
- Analysis and migration only ever publish into the fixed local staging file. The optional results-only installation only accepts a normal, non-redirected `Interface/AddOns/LocalGearAdvisor` path with an exactly compatible `Core.lua` and TOC.
- The canonical multi-profile state and its Lua projection are published under one shared OS lock. A path-bound journal binds old and new hash generations, restores controlled failures immediately, and only ever repairs known intermediate states after a process crash; a foreign generation is preserved fail-closed.
- Before a results-only publication, the target inventory, staging hash, and the byte-exact projection are all checked against the strictly validated canonical JSON state. An OS lock bound to the canonical target path (not the freely choosable receipt path) serializes every cooperating publisher for the same `Results.lua`. Locked directory identities plus write-/replace-denying handles on `Core.lua` and the TOC prevent an incompatible code swap during recovery and publication. Fresh WoW checks run immediately before every preparatory live-tree write, recovery link, rename, publish, and controlled cleanup; `running` and `unknown` refuse that mutation. This is a preflight guarantee, not an atomic process-start lock: the operator must keep WoW closed for the complete operation. The old generation is atomically moved into a unique backup outside `AddOns`; the new generation is only ever published create-if-absent and then read back and hashed. A persistent journal repairs a process crash between these steps. A concurrent foreign generation is never overwritten. After an already-verified publication, a later receipt, SavedVariables, or process failure no longer attempts an automatic rollback; the new generation and the backup are retained for safe inspection. The receipt and pending journal live entirely outside the WoW Retail tree; the target-bound publisher lock lives in the normal user temp directory and is additionally checked against the Retail tree. The receipt stores only a count and an aggregate digest for SavedVariables, never personal paths. Schema-2 DPS values are bounded to `0..10^12` and delta percentages to `±10^6`; anything larger is rejected fail-closed in both Python and Lua.
- **In-game import transport (new):** the transport blob is a small custom canonical grammar (never Lua source), tokenized byte by byte with hard bounds -- max 256 KiB total, max nesting depth 8, max 20,000 items per container, max 1,000,000 bytes per string, strict ascending unique dict keys, no NaN/Inf-like tokens, no leading-zero integers. It carries its own SHA-256 integrity digest (a pure-Lua implementation, since WoW's Lua 5.1 has no `bit32`/bitlib, cross-checked against Python's `hashlib` for many inputs including the real payload). Import.lua **never calls `load`/`loadstring`/any form of `eval`**; a malicious paste is always inert data, never executable code, and a decoded profile is validated against the exact same semantic schema `Results.lua` entries already satisfy before it can be applied.
- **Transactional SavedVariables apply (new):** `LocalGearAdvisorDB` is only ever written by one function, which validates fully first and only mutates on success -- a shape or semantic failure leaves the existing database completely untouched, byte for byte. Apply/delete replace or remove only the exact matching identity (region/realm/character/spec ID); every other entry is left exactly as it was. A one-step undo snapshot (`LocalGearAdvisorUndo`, a separate SavedVariable) records the identity and the profile before/after the change, and refuses to revert if that identity has since been touched by a newer import or edit -- so undo can never silently clobber unrelated, newer state. Undo is one-shot: it clears its own snapshot on success.
- The project never terminates WoW itself. `running` and `unknown` block fail-closed.
- Research bundles, runs, logs, and real character exports live under ignored directories and do not belong in git.

## Limits of the claim

A tooltip value is a comparison against the simulated baseline and the chosen scenario, not a
universal best-in-slot claim. Effects not modeled by SimC must never be interpreted as a value
of 0. Before any in-game installation, an independent review and explicit approval are
required.
